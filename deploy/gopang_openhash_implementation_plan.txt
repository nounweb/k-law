1. 개요 및 목표
================================================================================

1.1 배경
--------
현재 고팡(Gopang) 서버는 다음 두 가지 문제가 있다:

  문제 A: K-Law(DeepSeek API) 위법성 탐지가 대화 종료 후 실행되도록
          설계되어 있으나 (gopang_server.py의 /pdv/analyze/ 엔드포인트),
          실제 흐름이 올바르게 연결되어 있음. ← 이 부분은 유지.

  문제 B: OpenHash 네트워크 등록이 Telegram 채널 텍스트 posting으로
          임시 대체되어 있음. ← 이 부분을 OpenHash 시뮬레이션으로 교체.

1.2 목표
--------
대화 종료 시 다음 세 가지 작업이 순차적·병렬적으로 실행되어야 한다:

  [1] K-Law 위법성 탐지 (DeepSeek API 배치 분석) ← 현재 구현됨. 유지.
  [2] PDV 저장 (대화 내용 + 분석 결과 전체를 Phase 6 스펙으로 저장)
  [3] OpenHash 등록 (SHA-256 해시 → 시뮬레이션 계층 네트워크에 분산 등록)

1.3 시뮬레이션 범위
-------------------
실제 OpenHash 네트워크(ISP 인프라 기반 물리적 분산)는 현재 에뮬레이션 단계이므로,
아래와 같은 경량 시뮬레이션 구조로 구현한다:

  - 오라클 서버(gopang.net, 144.24.90.233) 한 대에서 모든 노드를 프로세스/
    인메모리 딕셔너리로 에뮬레이션
  - L1: 10개 노드 (읍면동 단위 시뮬레이션)
  - L2:  4개 노드 (시군구 단위 시뮬레이션)
  - L3:  3개 노드 (광역시도 단위 시뮬레이션)
  - L4:  2개 노드 (국가 단위 시뮬레이션)
  - L5:  1개 노드 (글로벌 단위 시뮬레이션)
  - 합계: 20개 노드 (모두 gopang_server.py 내 Python dict로 에뮬레이션)

  ※ 실제 배포 시 각 노드를 별도 서버/프로세스로 분리하면 됨.
     코드 구조는 실제 분산 환경을 고려하여 설계.

2. 현재 상태 분석
================================================================================

2.1 현재 대화 종료 흐름
-----------------------
[클라이언트]
  사용자가 "⏹ 대화 종료" 버튼 클릭
    → exitConv() 함수 실행
    → ws.close() (WebSocket 종료)
    → POST /pdv/analyze/{conv_id} 호출
    → 결과를 배치 분석 패널에 표시

[서버] POST /pdv/analyze/{conv_id}
  → 미분석 메시지 로드
  → run_batch_analysis() 호출 (DeepSeek API)
  → conv_analysis 테이블 저장
  → pdv_log 테이블 저장
  → anchor_telegram() 호출 (Telegram으로 해시 등록) ← 여기를 교체

2.2 변경이 필요한 부분
----------------------
  (1) anchor_telegram() → anchor_openhash()로 교체
      : Telegram posting 대신 OpenHash 시뮬레이션 네트워크에 등록

  (2) PDV 저장 내용 보강
      : Phase 6 스펙(KL-M-02)에 맞게 저장 항목 확장
        - S0: 간소 기록 (타임스탬프, 유형, 점수, 등급, 해시)
        - S1~S3: 전체 기록 (원문, Phase 0~5 전체 결과, 근거 법조항)

  (3) OpenHash 시뮬레이션 모듈 신설
      : PLSM (확률적 계층 선택) + 계층별 노드 등록 에뮬레이션

  (4) PDV 서랍 분류
      : 6개 서랍(금융/의료/교육/행정/교통/일반) 자동 분류

  (5) 변경하지 않는 부분
      : K-Law(DeepSeek) 배치 분석 로직 전체, 인증/WS/메시지 전송 로직 전체


================================================================================
3. 대화 종료 시 처리 흐름 (핵심 설계)
================================================================================

3.1 전체 시퀀스
---------------

  [클라이언트] "⏹ 대화 종료" 버튼 클릭
       │
       ▼
  [클라이언트] exitConv()
    - ws.close()
    - POST /pdv/analyze/{conv_id} 호출 (기존과 동일)
    - 로딩 스피너 표시 ("배치 분석 중...")
       │
       ▼
  [서버] POST /pdv/analyze/{conv_id}
    ┌──────────────────────────────────────────────────────┐
    │ Step 1. 메시지 로드 (DB에서 대화 내용 전체 조회)       │
    │                                                        │
    │ Step 2. K-Law 배치 분석 (DeepSeek API)                │
    │         run_batch_analysis(messages)                   │
    │         ← 기존 코드 유지                               │
    │                                                        │
    │ Step 3. PDV 저장                                       │
    │         save_to_pdv(conv_id, messages, analysis)      │
    │         - 등급별 저장 항목 차등 (S0 간소 / S1~S3 전체) │
    │         - PDV 서랍 분류 (6개 카테고리)                  │
    │         - AES-256 암호화 (시뮬레이션: 해시로 대체)      │
    │                                                        │
    │ Step 4. OpenHash 등록                                  │
    │         anchor_openhash(payload)                       │
    │         - PLSM으로 기록 계층 결정                       │
    │         - 해당 계층 노드에 해시 등록                    │
    │         - 상위 계층으로 Merkle 루트 전파               │
    │         - anchor_id (L1~L5 노드 주소 포함) 반환        │
    │                                                        │
    │ Step 5. 결과 반환                                       │
    │         {K-Law 분석 결과 + PDV 저장 확인 + anchor_id}  │
    └──────────────────────────────────────────────────────┘
       │
       ▼
  [클라이언트] 결과 표시
    - 배치 분석 패널: K-Law 분석 결과
    - PDV 패널: 저장 완료 + anchor_id
    - OpenHash 패널: 등록된 계층 정보

3.2 병렬 처리 전략
------------------
  Step 2 (K-Law)와 Step 3 (PDV 저장)은 순차 실행.
  Step 4 (OpenHash 등록)는 Step 3 완료 후 실행 (해시 생성에 PDV 내용 필요).

  이유: PDV 해시 = SHA-256(대화내용 + 분석결과 + 타임스탬프)
        이 해시가 OpenHash 등록의 입력값이 되므로 순차 실행이 맞음.

  총 소요 시간 추정:
    - K-Law 분석: 5~30초 (DeepSeek API, 메시지 수에 따라 변동)
    - PDV 저장: < 50ms (SQLite)
    - OpenHash 등록: < 10ms (인메모리 시뮬레이션)
    - 합계: K-Law 분석 시간이 지배적

4. PDV(Personal Data Vault) 설계
================================================================================

4.1 스펙 (KL-M-02 Phase 6 기준)
---------------------------------

  등급별 저장 항목:

  S0 (안전) — 간소 기록
  ┌──────────────────────────────────────┐
  │ - 소통 일시 (타임스탬프)              │
  │ - 소통 유형 (텍스트/문서/음성)        │
  │ - FINAL_score (발신·수신)            │
  │ - 등급: S0                           │
  │ - OpenHash 등록 해시값               │
  │ 보존 기간: 90일                       │
  └──────────────────────────────────────┘

  S1~S3 — 전체 기록
  ┌──────────────────────────────────────┐
  │ - 소통 일시 + OpenHash 등록 증명      │
  │ - 소통 원문 (암호화 저장)             │
  │ - Fast-Path 탐지 결과                 │
  │   (키워드, 등급, 판정 근거)           │
  │ - K-Law 배치 분석 결과               │
  │   (등급, 점수, 요약, 법적 소견)       │
  │ - 근거 법조항 목록                   │
  │ - 이의 제기 이력 (해당 시)           │
  │ 보존 기간: 5년                        │
  └──────────────────────────────────────┘

4.2 PDV 서랍 분류 (6개 카테고리)
----------------------------------
  대화 내용 키워드 기반 자동 분류:

  FINANCIAL  (금융 서랍): 계좌, 이체, 송금, 대출, 보험, 투자, 주식, 세금
  MEDICAL    (의료 서랍): 진단, 처방, 병원, 의사, 치료, 약, 수술, 증상
  EDUCATION  (교육 서랍): 학교, 성적, 입학, 자격증, 교육, 학위, 수강
  ADMIN      (행정 서랍): 민원, 계약, 공문, 서류, 신청, 허가, 행정
  TRANSPORT  (교통 서랍): 차량, 교통, 운전, 사고, 면허, 주차
  GENERAL    (일반 서랍): 위 5개에 해당하지 않는 모든 소통

  분류 알고리즘: 키워드 빈도 기반 (간단 구현)
    → 각 서랍의 키워드 딕셔너리와 대화 내용을 대조
    → 가장 많이 매칭된 서랍으로 분류
    → 매칭 없으면 GENERAL

4.3 신규 DB 테이블: pdv_records
---------------------------------
  CREATE TABLE pdv_records (
      pdv_record_id  TEXT PRIMARY KEY,
      conv_id        TEXT NOT NULL,
      user_id        TEXT NOT NULL,
      grade          TEXT NOT NULL,           -- S0/S1/S2/S3
      drawer         TEXT NOT NULL,           -- FINANCIAL/MEDICAL/...
      content_hash   TEXT NOT NULL,           -- SHA-256(대화 원문)
      content_enc    TEXT,                    -- 암호화된 원문 (S1~S3만)
      analysis_json  TEXT,                    -- K-Law 분석 결과 JSON
      fast_path_json TEXT,                    -- Fast-Path 결과 JSON
      legal_refs     TEXT DEFAULT '[]',       -- 근거 법조항 JSON 배열
      anchor_id      TEXT,                    -- OpenHash anchor ID
      anchor_tier    TEXT,                    -- 등록된 계층 (L1~L5)
      retention_days INTEGER DEFAULT 90,      -- 보존 기간 (S0=90, S1~S3=1825)
      created_at     TEXT DEFAULT (datetime('now')),
      expires_at     TEXT                     -- 만료일
  );

5.2 계층 매핑 테이블
---------------------
  각 L1 노드가 어느 L2, L3, L4, L5에 귀속되는지 고정 매핑:

  L1-001 ~ L1-005 → L2-001 → L3-001 → L4-001 → L5-001
  L1-006 ~ L1-009 → L2-003 → L3-001 → L4-001 → L5-001
  L1-010          → L2-002 → L3-001 → L4-002 → L5-001

5.3 PLSM (확률적 계층 선택 모듈)
----------------------------------
  OpenHash 논문 §4.1 알고리즘 1을 단순화하여 구현:

  입력: content_hash (SHA-256), timestamp, overall_grade (S0~S3)
  출력: 등록할 L1 노드 ID, 전파할 상위 계층 목록

  Step 1: h1 = SHA-256(content_hash + timestamp)
  Step 2: r  = int(h1, 16) % 1000
  Step 3: 중요도 점수 산출
          score = {"S0": 10, "S1": 35, "S2": 65, "S3": 90}[overall_grade]
          (K-Law 분석의 overall_grade를 중요도 점수로 매핑)
  Step 4: score 기반 계층 선택 확률 테이블 적용

  [계층 선택 확률 테이블]
  ┌──────────────────────────────────────────────────────────┐
  │ 중요도      │ L1(%) │ L2(%) │ L3(%) │ L4(%) │ L5(%)    │
  ├──────────────────────────────────────────────────────────┤
  │ 저(S0,<25)  │  50   │  30   │  12   │   6   │   2      │
  │ 보통(S1,35) │  30   │  30   │  20   │  15   │   5      │
  │ 고(S2,65)   │  15   │  20   │  30   │  25   │  10      │
  │ 긴급(S3,90) │   5   │  15   │  25   │  30   │  25      │
  └──────────────────────────────────────────────────────────┘
  ※ 선택된 계층이 L1이면 L1 노드에 등록 후 L2→L3→L4→L5로 Merkle 루트 전파
  ※ 선택된 계층이 L3이면 L3 노드에 등록 후 L4→L5로만 전파 (L1/L2는 해시만 참조)

  Step 5: r값으로 L1 노드 선택 (10개 노드 균등 분배: r % 10)

5.4 OpenHash 등록 절차 (시뮬레이션)
-------------------------------------
  각 노드는 Python dict로 구현:
  node = {
      "node_id": "L1-001",
      "tier": "L1",
      "name": "제주시_이도1동",
      "chain": [],          # 해시 체인 (리스트)
      "merkle_root": None,  # 현재 Merkle 루트
      "parent": "L2-001"    # 상위 노드 ID
  }

  등록 알고리즘:
  1. entry_hash = SHA-256(content_hash ∥ timestamp ∥ conv_id)
  2. prev_hash  = node["chain"][-1]["hash"] if chain else "0"*64
  3. chain_hash = SHA-256(prev_hash ∥ entry_hash ∥ len(chain))
  4. node["chain"].append({
         "seq": len(node["chain"]),
         "entry_hash": entry_hash,
         "chain_hash": chain_hash,
         "timestamp": datetime.utcnow().isoformat(),
         "conv_id": conv_id
     })
  5. node["merkle_root"] = compute_merkle_root(node["chain"])

  상위 계층 전파:
  1. L1 등록 완료 후 → L2에 merkle_root 전파
  2. L2 Merkle 루트 갱신 후 → L3에 전파
  3. L3 → L4 → L5 순으로 반복

  anchor_id 형식:
  "OH-{tier}-{node_id}-{seq}-{chain_hash[:16]}"
  예: "OH-L1-L1001-42-a3f7c9d2e1b80514"

5.5 신규 DB 테이블: openhash_nodes (시뮬레이션 상태 영속화)
-------------------------------------------------------------
  CREATE TABLE openhash_nodes (
      node_id      TEXT PRIMARY KEY,
      tier         TEXT NOT NULL,     -- L1/L2/L3/L4/L5
      name         TEXT NOT NULL,
      parent_id    TEXT,              -- 상위 노드 ID (L5는 NULL)
      chain_json   TEXT DEFAULT '[]', -- 해시 체인 JSON
      merkle_root  TEXT,              -- 현재 Merkle 루트
      entry_count  INTEGER DEFAULT 0,
      updated_at   TEXT DEFAULT (datetime('now'))
  );

  CREATE TABLE openhash_entries (
      entry_id     TEXT PRIMARY KEY,
      node_id      TEXT NOT NULL,
      seq          INTEGER NOT NULL,
      conv_id      TEXT NOT NULL,
      entry_hash   TEXT NOT NULL,
      chain_hash   TEXT NOT NULL,
      tier         TEXT NOT NULL,
      timestamp    TEXT NOT NULL
  );

5.6 Merkle 루트 계산 (간소화)
-------------------------------
  시뮬레이션용 간소화된 Merkle 루트:

  def compute_merkle_root(entries):
      if not entries:
          return "0" * 64
      hashes = [e["chain_hash"] for e in entries]
      while len(hashes) > 1:
          if len(hashes) % 2 != 0:
              hashes.append(hashes[-1])  # 홀수면 마지막 복제
          hashes = [
              hashlib.sha256((hashes[i] + hashes[i+1]).encode()).hexdigest()
              for i in range(0, len(hashes), 2)
          ]
      return hashes[0]

5.7 위변조 검증 API (향후 확장용)
-----------------------------------
  GET /openhash/verify/{conv_id}
  → conv_id에 해당하는 anchor_id로 해시 체인을 재계산
  → 저장된 chain_hash와 비교
  → 일치: {"verified": true, "tampered": false}
  → 불일치: {"verified": false, "tampered": true}

  ※ 현재 구현에서는 시뮬레이션이므로 항상 verified=true 반환 가능
     (실제 배포 시 분산 노드 간 검증으로 교체)

  [B] plsm_select_tier(content_hash: str, timestamp: str, grade: str) -> str
  ──────────────────────────────────────────────────────────────────────────────
  역할: PLSM으로 등록 계층 결정 (L1~L5)
  반환: "L1", "L2", "L3", "L4", "L5" 중 하나

  구현:
    h1 = sha256(content_hash + timestamp)
    r  = int(h1, 16) % 100  # 0~99
    grade_to_prob = {
        "S0": [50, 30, 12, 6, 2],   # L1~L5 누적 분포
        "S1": [30, 60, 80, 95, 100],
        "S2": [15, 35, 65, 90, 100],
        "S3": [ 5, 20, 45, 75, 100],
    }
    probs = grade_to_prob.get(grade, grade_to_prob["S0"])
    cumulative = [0, probs[0], probs[0]+probs[1]-30, ...]
    → r 값이 해당 누적 구간에 속하는 계층 반환

  ※ 정확한 누적 확률 계산:
    S0: L1→r<50, L2→50≤r<80, L3→80≤r<92, L4→92≤r<98, L5→r≥98
    S1: L1→r<30, L2→30≤r<60, L3→60≤r<80, L4→80≤r<95, L5→r≥95
    S2: L1→r<15, L2→15≤r<35, L3→35≤r<65, L4→65≤r<90, L5→r≥90
    S3: L1→r<5,  L2→5≤r<20,  L3→20≤r<45, L4→45≤r<75, L5→r≥75

  [D] async anchor_openhash(conv_id, content_hash, grade, timestamp) -> dict
  ────────────────────────────────────────────────────────────────────────────
  역할: OpenHash 시뮬레이션 네트워크에 해시 등록
  반환: {
      "anchor_id": "OH-L1-L1001-42-a3f7c9d2",
      "tier": "L1",
      "node_id": "L1-001",
      "node_name": "제주시_이도1동",
      "chain_hash": "...",
      "merkle_root": "...",
      "propagated_to": ["L2-001", "L3-001", "L4-001", "L5-001"],
      "timestamp": "..."
  }

  구현:
    1. tier = plsm_select_tier(content_hash, timestamp, grade)
    2. l1_idx = int(sha256(content_hash), 16) % 10  → L1 노드 선택
    3. 선택된 계층이 L1이면 L1 노드에 등록 → 상위 계층으로 전파
       선택된 계층이 L3이면 L3 노드에 직접 등록 → L4→L5로만 전파
    4. entry_hash = sha256(content_hash + timestamp + conv_id)
    5. chain에 엔트리 추가, merkle_root 갱신
    6. DB (openhash_nodes, openhash_entries) 업데이트
    7. anchor_id 생성 후 반환

  ※ 계층 전파 경로 (entry_tier별):
    L1 → L1 등록 → L2 전파 → L3 전파 → L4 전파 → L5 전파
    L2 → L2 등록 → L3 전파 → L4 전파 → L5 전파
    L3 → L3 등록 → L4 전파 → L5 전파
    L4 → L4 등록 → L5 전파

    * PDV: FINANCIAL 서랍, 전체 기록 (5년 보존)
    * OpenHash: L3~L5에 등록 (S3이므로 높은 계층 확률 높음)
    * anchor_id: OH-L3-... 또는 OH-L4-...

  시나리오 3: OpenHash 네트워크 현황 확인
  ─────────────────────────────────────────
  - GET /openhash/status 직접 호출
  - 예상 결과: 20개 노드 목록, 각 노드의 entry_count, merkle_root

  시나리오 4: 위변조 검증
  ─────────────────────────
  - GET /openhash/verify/{conv_id}
  - 예상 결과: verified=true, anchor_id, tier, 전파 경로

================================================================================
부록 B: 향후 실제 분산 배포 시 변경 사항
================================================================================

  현재 시뮬레이션 → 실제 배포 전환 시 변경할 부분:

  1. openhash_nodes 테이블의 각 노드를 별도 서버/컨테이너로 분리
  2. anchor_openhash() 함수에서 HTTP/gRPC로 원격 노드에 등록 요청
  3. ILMV 하향 감사 스케줄러 추가 (APScheduler 등)
  4. LPBFT 비상 합의 로직 추가 (위변조 탐지 시)
  5. L2→L1 100% 스트리밍 감사 추가
  6. BLS 집계 서명으로 교체 (현재는 SHA-256만 사용)
  7. AES-256 실제 암호화 (현재는 hash만)

  ※ 코드 구조는 처음부터 이 확장을 고려하여 설계:
     - anchor_openhash()는 내부적으로 각 노드를 독립 객체로 처리
     - DB 스키마는 분산 배포 시 그대로 사용 가능
     - API 인터페이스 변경 없음
